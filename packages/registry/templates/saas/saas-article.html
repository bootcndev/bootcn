How we cut our page load time in half

Six months, four fixes and one surprising culprit: what it took to get the dashboard under one second.

LF

Lena Fischer Staff engineer

20 Nov 2026 · 8 min read

Measure before you change anything

We started with a hunch: the dashboard felt slow. Hunches are a poor guide, so for two weeks we changed nothing and measured everything: real-user timings from every page view, split by country, device and plan.

The numbers told a clearer story than our hunch. The median load was fine; the slowest tenth of page views took more than four seconds, and almost all of them came from accounts with large projects.

The surprising culprit

We expected the database. It was the browser. One chart rendered every data point it was given, and large projects gave it tens of thousands.

The fastest code is the code that never runs. We stopped drawing points nobody could see.

Downsampling to the width of the chart, in pixels, kept the shape of every line and cut the work by more than ninety percent.

Four fixes that mattered

  1. Downsample charts to one point per pixel.
  2. Stream the first screen and load the rest after it.
  3. Cache project summaries for a minute instead of rebuilding them on every visit.
  4. Ship less JavaScript: a date library we used in one place was a quarter of the bundle. 
const step = Math.ceil(points.length / chart.width); // one point per pixel

The results

Page load, slowest tenth of visits
Page Before After
Dashboard 4.2 s 1.9 s
Project 5.1 s 2.3 s
Reports 3.8 s 1.7 s

Support tickets mentioning speed fell by two thirds the month after. The work is never done, but we now check these numbers every week.
